## 3. 무엇을 만들었나 (쉬운 설명)

### 3.01 — DB 두 개를 갈라놨습니다

**문제**: LangGraph(대화 흐름 엔진)가 자기 데이터를 저장할 DB 주소를 못 찾으면, 경험 맵 DB에 자기 테이블을 만들어버리는 상태였습니다. 경험 맵 DB는 메인 서버 것이고 우리는 읽기만 해야 하는데도요.

**한 일**: 그 자동 대체(fallback)를 없앴습니다. 이제 checkpoint 전용 DB 주소가 없으면 서버가 아예 안 켜집니다.

> ⚠️ **배포 주의**: `CHECKPOINT_DATABASE_URL` 환경변수를 **먼저** 넣고 코드를 배포해야 합니다. 순서가 바뀌면 앱이 안 뜹니다.

**덤으로 발견한 것**: 경험 맵 DB 연결 코드가 작성만 되어 있고 **어디서도 호출되지 않는 상태**였습니다. 이번에 처음으로 앱에 연결했습니다.

### 3.02 — 데이터의 모양을 정했습니다

AI가 만들어내는 결과물의 형식을 코드로 못박았습니다. 이후 모든 작업이 이 형식을 기준으로 돌아갑니다.

**중요한 건 "프롬프트로 부탁"하지 않고 "타입으로 차단"한 것 셋입니다.**

| 막은 것 | 왜 |
| --- | --- |
| 문장 다듬기 단계가 블록 위치를 바꾸는 것 | 위치를 바꿀 수 있는 필드를 아예 안 만듦 |
| 블록의 부모를 두 가지 방식으로 동시 지정 | 둘 중 하나만 쓰도록 검증 |
| AI가 블록의 단계(level)·순서를 정하는 것 | 메인 서버가 계산하는 값이라 필드에서 제외 |

AI에게 부탁하면 대체로 지키지만 가끔 어깁니다. 타입으로 막으면 어긴 순간 걸립니다.

### 3.08 — 대화 데이터의 그릇을 만들었습니다

대화가 이어지는 동안 들고 다니는 데이터를 정의했습니다. 핵심은 **두 종류로 나눈 것**입니다.

| 종류 | 예 | 언제 지우나 |
| --- | --- | --- |
| 세션 데이터 | 사용자 ID, 직전 턴의 제안 | 안 지움 |
| 턴 데이터 | 이번에 입력한 내용, 중간 계산 결과 | **요청마다 초기화** |

**왜 중요하냐면**: 턴 데이터를 안 지우면 **이전 요청에서 만든 블록이 다음 요청에 섞여서 저장됩니다.** 사용자 입장에서는 하지도 않은 말이 자기 경험 정리에 들어가 있는 겁니다.

### 3.07 — 파일 업로드를 처리합니다

사용자가 이력서·포트폴리오를 올리면 검사하고, GCS에 잠깐 뒀다가, 텍스트를 뽑아낸 뒤 바로 지웁니다.

**검사를 세 겹으로 합니다.**

| 검사 | 막는 것 |
| --- | --- |
| 파일 형식이 허용 목록에 있나 | 지원 안 하는 형식 |
| 확장자와 형식이 맞나 | `문서.png`인데 PDF라고 우기는 경우 |
| 실제 파일 내용이 그 형식인가 | 확장자만 바꾼 위조 파일 |

앞의 둘은 사용자가 마음대로 정할 수 있는 값이라, 실제 파일 앞부분을 직접 열어봐야 합니다.

**개인정보**: 이력서에는 이름·전화번호·주민번호가 들어 있습니다. 파일명과 내용을 로그에 절대 안 남기고, 이걸 테스트로 고정했습니다.

### 3.09 — 프론트가 직접 붙을 때의 인증

원래는 프론트 → 메인 서버 → AI 서버였는데, 실시간 스트리밍 때문에 **프론트가 AI 서버에 직접 붙습니다.** 그래서 AI 서버가 직접 인증해야 합니다.

메인 서버가 로그인 확인 후 5분짜리 **티켓**을 발급하고, AI 서버는 그걸 검증합니다.

**검증 순서가 중요합니다.**

```text
① 서명이 진짜인가        → 아니면 거부
② 유효기간이 지났나       → 지났으면 거부
③ 이 티켓이 이 세션 것인가 → 아니면 거부  ← 세션 탈취를 막는 단계
```

③이 없으면 A 사용자의 유효한 티켓으로 B 사용자의 세션을 건드릴 수 있습니다.

**또 하나**: 파일이 최대 30MB 들어오는데, 인증에 실패한 요청의 내용은 **한 바이트도 읽지 않고** 거부합니다. 안 그러면 아무나 서버에 30MB씩 밀어넣을 수 있습니다.

## 5. 설계 문서와 다르게 간 부분

작업하면서 설계 문서의 문제를 발견하거나 판단을 바꾼 곳입니다. **문서 갱신이 필요합니다.**

| # | 내용 | 어디 |
| --- | --- | --- |
| 1 | 템플릿 슬롯 생성 규칙이 문서 안에서 **서로 반대로** 적혀 있었음 → 수정 | 통합 문서 3-1 / 3-2 |
| 2 | Fallback 문구가 4가지 상황에 전부 같았음 → 상황별로 분리 | 통합 문서 5-11 |
| 3 | `parent_ref` / `parent_item_id` 역할이 겹쳐 보였음 → 경계 명확화 | 통합 문서 5-5 |
| 4 | gap 분석 노드가 **개발 순서에 항목이 없었음** → 별도 태스크로 추가 | 통합 문서 9절 |
| 5 | `GapOutput`을 **두 모델로 분리** (AI가 보는 별칭용 / 저장용) | 통합 문서 8-1 |
| 6 | `429`(요청 과다) 오류가 **API 명세 오류표에 없음** → 추가 필요 | API 명세 2-3 |

1~4는 이미 문서에 반영했습니다. 5~6은 **아직 반영 안 됐습니다.**

### 왜 이런 판단을 했나

**Fallback 문구 분리 (2번)**: 원래는 "파일을 못 읽었을 때"와 "지원 안 하는 요청일 때" 모두 "아직 지원하지 않는 기능이에요."가 나갔습니다. 파일이 손상돼서 실패한 사용자는 이 문구를 보면 다른 파일로 다시 올려볼 생각을 못 합니다.

**GapOutput 분리 (5번)**: AI에게는 실제 DB ID를 안 보여줍니다 (지어내기 때문). 대신 임시 별칭을 씁니다. 그래서 AI가 내놓는 형식과 DB에 저장하는 형식이 다를 수밖에 없어서 모델을 둘로 나눴습니다.

## 6. 테스트가 잡아낸 버그 3개

직접 짠 코드에서 테스트가 잡은 실제 결함입니다.

**① 한글 텍스트 파일이 전부 거부되던 문제**

파일 앞 8바이트로 형식을 검사하는데, 한글은 한 글자가 3바이트입니다. 8은 3의 배수가 아니라서 **거의 항상 글자 중간이 잘립니다.** 잘린 조각은 올바른 한글이 아니라 판정돼서, 정상적인 한글 `.txt`가 모두 거부되는 상태였습니다.

**② 정리 함수가 일부 항목을 안 지우던 문제**

대화 성공 후 큰 데이터를 비우는 함수가 "이미 있는 항목만" 비웠습니다. 원래 없던 항목은 그대로 없는 채로 남아서, 나중에 읽으려는 코드가 오류를 낼 수 있었습니다.

**③ 테스트 자체의 가정 오류**

"파일 마지막 글자가 잘리면 거부되나"를 확인하려는데, 하필 마지막 글자가 마침표(1바이트)라 잘라도 멀쩡했습니다. 3바이트 글자를 자르도록 고쳤습니다.

### ~~`slot_id` 목록 미확정~~ → 해소됨 (2026-08-09)

메인 서버에서 카탈로그를 받아 **38개가 확정**됐습니다. 통합 문서 3-0·3-2·3-3·3-4에 반영했습니다.

```text
카테고리 슬롯 (4단계)   10개   ← 카테고리 만들 때 함께 생성
하위 템플릿   (5단계)   28개   ← 담당업무 1종×4 + 문제해결 6종×4
                        38개
```

**받고 나서 알게 된 것**: 식별자 형식이 단계에 따라 다릅니다. 4단계는 점이 하나(`DETAIL.MOTIVATION`), 5단계는 둘(`PROBLEM_SOLVING.TROUBLESHOOTING.CAUSE`)입니다. **점 개수만 세면 단계를 알 수 있습니다.** API 명세는 5단계 형식만 적어놨어서 정정했습니다.

**앵커 규칙**도 새로 들어왔습니다. 5단계 블록은 아무 데나 붙지 못하고, 반드시 `TASK.SUMMARY` 또는 `PROBLEM_SOLVING.SUMMARY`로 만든 4단계 블록 아래에 붙습니다. 담당업무는 업무 하나당, 문제해결은 에피소드 하나당 한 벌이며 한 활동에 여러 벌이 들어갈 수 있습니다.

이제 **3.15(블록 구조화)를 막는 것이 없습니다.**
