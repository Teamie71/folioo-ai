## 3. 무엇을 만들었나 (쉬운 설명)

### 3.01 — DB 두 개를 갈라놨습니다

**문제**: LangGraph(대화 흐름 엔진)가 자기 데이터를 저장할 DB 주소를 못 찾으면, 경험 맵 DB에 자기 테이블을 만들어버리는 상태였습니다. 경험 맵 DB는 메인 서버 것이고 우리는 읽기만 해야 하는데도요.

**한 일**: 그 자동 대체(fallback)를 없앴습니다. 이제 checkpoint 전용 DB 주소가 없으면 서버가 아예 안 켜집니다.

> ⚠️ **배포 주의**: `CHECKPOINT_DATABASE_URL` 환경변수를 **먼저** 넣고 코드를 배포해야 합니다. 순서가 바뀌면 앱이 안 뜹니다.

**덤으로 발견한 것**: 경험 맵 DB 연결 코드가 작성만 되어 있고 **어디서도 호출되지 않는 상태**였습니다. 이번에 처음으로 앱에 연결했습니다.

### 3.02 — 데이터의 모양을 정했습니다

AI가 만들어내는 결과물의 형식을 코드로 못박았습니다. 이후 모든 작업이 이 형식을 기준으로 돌아갑니다.

**중요한 건 "프롬프트로 부탁"하지 않고 "타입으로 차단"한 것 셋입니다.**

| 막은 것 | 왜 |
| --- | --- |
| 문장 다듬기 단계가 블록 위치를 바꾸는 것 | 위치를 바꿀 수 있는 필드를 아예 안 만듦 |
| 블록의 부모를 두 가지 방식으로 동시 지정 | 둘 중 하나만 쓰도록 검증 |
| AI가 블록의 단계(level)·순서를 정하는 것 | 메인 서버가 계산하는 값이라 필드에서 제외 |

AI에게 부탁하면 대체로 지키지만 가끔 어깁니다. 타입으로 막으면 어긴 순간 걸립니다.

### 3.07 — 파일 업로드를 처리합니다

사용자가 이력서·포트폴리오를 올리면 검사하고, GCS에 잠깐 뒀다가, 텍스트를 뽑아낸 뒤 바로 지웁니다.

**검사를 세 겹으로 합니다.**

| 검사 | 막는 것 |
| --- | --- |
| 파일 형식이 허용 목록에 있나 | 지원 안 하는 형식 |
| 확장자와 형식이 맞나 | `문서.png`인데 PDF라고 우기는 경우 |
| 실제 파일 내용이 그 형식인가 | 확장자만 바꾼 위조 파일 |

앞의 둘은 사용자가 마음대로 정할 수 있는 값이라, 실제 파일 앞부분을 직접 열어봐야 합니다.

**개인정보**: 이력서에는 이름·전화번호·주민번호가 들어 있습니다. 파일명과 내용을 로그에 절대 안 남기고, 이걸 테스트로 고정했습니다.

### 3.08 — 대화 데이터의 그릇을 만들었습니다

대화가 이어지는 동안 들고 다니는 데이터를 정의했습니다. 핵심은 **두 종류로 나눈 것**입니다.

| 종류 | 예 | 언제 지우나 |
| --- | --- | --- |
| 세션 데이터 | 사용자 ID, 직전 턴의 제안 | 안 지움 |
| 턴 데이터 | 이번에 입력한 내용, 중간 계산 결과 | **요청마다 초기화** |

**왜 중요하냐면**: 턴 데이터를 안 지우면 **이전 요청에서 만든 블록이 다음 요청에 섞여서 저장됩니다.** 사용자 입장에서는 하지도 않은 말이 자기 경험 정리에 들어가 있는 겁니다.

### 3.09 — 프론트가 직접 붙을 때의 인증

원래는 프론트 → 메인 서버 → AI 서버였는데, 실시간 스트리밍 때문에 **프론트가 AI 서버에 직접 붙습니다.** 그래서 AI 서버가 직접 인증해야 합니다.

메인 서버가 로그인 확인 후 5분짜리 **티켓**을 발급하고, AI 서버는 그걸 검증합니다.

**검증 순서가 중요합니다.**

```text
① 서명이 진짜인가        → 아니면 거부
② 유효기간이 지났나       → 지났으면 거부
③ 이 티켓이 이 세션 것인가 → 아니면 거부  ← 세션 탈취를 막는 단계
```

③이 없으면 A 사용자의 유효한 티켓으로 B 사용자의 세션을 건드릴 수 있습니다.

**또 하나**: 파일이 최대 30MB 들어오는데, 인증에 실패한 요청의 내용은 **한 바이트도 읽지 않고** 거부합니다. 안 그러면 아무나 서버에 30MB씩 밀어넣을 수 있습니다.

### 3.04 — 누가 무엇을 실행 중인지 추적합니다

한 사용자가 창을 두 개 열고 동시에 요청하면? 서버가 여러 대인데 같은 요청이 두 곳에 들어가면? 처리 중에 서버가 죽으면?

**전부 DB가 막습니다.** 애플리케이션 코드로 잠그지 않습니다.

| 상황 | 결과 |
| --- | --- |
| 같은 세션에 요청이 이미 실행 중 | 거부 (409) |
| 같은 요청을 다시 보냄 (완료됨) | 저장된 결과를 그대로 재전송 |
| 같은 요청 번호에 다른 내용 | 거부 — 실수로 덮어쓰는 걸 막음 |
| 실패한 요청을 채팅으로 재시도 | 거부 — 재시도 전용 API를 쓰라고 안내 |

**서버가 죽었을 때**: 실행 중인 요청은 30초마다 "나 살아있다"고 갱신합니다(lease). 갱신이 끊기면 5분 뒤 그 요청을 실패로 바꿔 세션을 풀어줍니다. 안 그러면 그 사용자는 영영 새 요청을 못 보냅니다.

**실제로 확인했습니다** — 8개 요청을 동시에 넣어 정확히 1개만 성공하는 것, 10개 동시 세션 생성이 1개로 모이는 것.

### 3.10 — API와 실시간 스트림

드디어 밖에서 부를 수 있는 문이 생겼습니다.

| 경로 | 하는 일 |
| --- | --- |
| `POST /sessions` | 세션 생성 (메인 서버가 호출) |
| `POST /chat/stream` | 채팅 + 파일 → **실시간 진행 상황 스트림** |
| `POST /retry/stream` | 실패한 요청 재시도 |
| `GET /state` | 세션 상태 (새로고침 시) |
| `GET /requests/{id}` | 결과 복구 (연결이 끊겼을 때) |

**설계에서 신경 쓴 것**: 실패할 수 있는 일은 **스트림을 열기 전에** 다 끝냅니다. 파일 검사, 요청 중복 확인 같은 것들입니다.

스트림을 연 뒤에 거절하면 프론트가 곤란해집니다 — HTTP 응답은 "성공(200)"인데 그 안에 오류가 들어 있는 형태라, 처리 코드를 두 벌 짜야 합니다.

**AI는 아직 가짜입니다.** 노드 진행 상황과 결과 문구는 고정된 값입니다. 3.17에서 진짜 그래프로 바뀝니다.

## 6. 테스트가 잡아낸 버그

**① 한글 텍스트 파일이 전부 거부되던 문제**

파일 앞 8바이트로 형식을 검사하는데, 한글은 한 글자가 3바이트입니다. 8은 3의 배수가 아니라서 **거의 항상 글자 중간이 잘립니다.** 잘린 조각은 올바른 한글이 아니라 판정돼서, 정상적인 한글 `.txt`가 모두 거부되는 상태였습니다.

**② 정리 함수가 일부 항목을 안 지우던 문제**

대화 성공 후 큰 데이터를 비우는 함수가 "이미 있는 항목만" 비웠습니다. 원래 없던 항목은 그대로 없는 채로 남아서, 나중에 읽으려는 코드가 오류를 낼 수 있었습니다.

**③ 3-4 표 24행이 깨진 것**

문서에 `slot_id` 열을 스크립트로 넣다가 구분 기호를 지워, 문제해결 템플릿 6종 표가 전부 2열로 뭉개졌습니다. 검사 스크립트가 헤더만 보고 데이터 행은 안 봐서 못 잡았습니다.

### 서버를 실제로 띄워서만 잡힌 것

단위 테스트로는 절대 안 잡히는 종류입니다.

**④ Repository를 앱에 연결하지 않았음**

3.04에서 함수는 만들었는데 앱 시작 코드에 배선하지 않았습니다. 테스트는 객체를 직접 주입해서 돌리니 통과했고, **실제 서버의 첫 API 호출에서 500**이 났습니다.

**⑤ 복구 응답의 데이터 형태가 달랐음**

연결이 끊긴 뒤 결과를 다시 받을 때, 스트림으로 받았을 내용과 **다른 형태**가 나가고 있었습니다. 제안 항목에서 "어느 블록에 대한 제안인지" 경로가 빠졌습니다.

## 7. 지금 막혀 있는 것

### 메인 서버 대기

| 필요한 것 | 막는 태스크 | 급한 정도 |
| --- | --- | --- |
| **`block` / `block_kind` 테이블 정의** | 3.05 → 3.14, 3.15 | **가장 큼** |

| `POST /commit` 커밋 API | 3.18 | 나중 (mock으로 진행 가능) |

**`block` 스키마가 지금 가장 값어치 있는 요청입니다.** migration 전체가 아니라 **두 테이블 정의만** 있으면 됩니다. 명세에 조회 쿼리와 제약은 있는데 테이블 정의가 없어서, 추측해서 만들면 나중에 다시 짜야 합니다.

### ~~`slot_id` 목록 미확정~~ → 해소됨 (2026-08-09)

메인 서버에서 카탈로그를 받아 **38개가 확정**됐습니다.

```text
카테고리 슬롯 (4단계)   10개   ← 카테고리 만들 때 함께 생성
하위 템플릿   (5단계)   28개   ← 담당업무 1종×4 + 문제해결 6종×4
                        38개
```

**받고 나서 알게 된 것**: 식별자 형식이 단계에 따라 다릅니다. 4단계는 점이 하나(`DETAIL.MOTIVATION`), 5단계는 둘(`PROBLEM_SOLVING.TROUBLESHOOTING.CAUSE`)입니다. **점 개수만 세면 단계를 알 수 있습니다.**

**앵커 규칙**도 새로 들어왔습니다. 5단계 블록은 아무 데나 붙지 못하고, 반드시 `TASK.SUMMARY` 또는 `PROBLEM_SOLVING.SUMMARY`로 만든 4단계 블록 아래에 붙습니다.
